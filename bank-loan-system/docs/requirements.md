# Requirements

## 1. Цель системы

Автоматизировать обработку заявок на потребительский кредит — от получения заявки до предварительного решения.

## 2. Акторы

| Актор | Ответственность |
|---|---|
| Клиент | Подаёт заявку и получает результат |
| REST API | Принимает и валидирует запросы |
| Application Service | Управляет жизненным циклом заявки |
| Verification Service | Проверяет данные заявки |
| Scoring Service | Рассчитывает кредитный score |
| PostgreSQL | Хранит заявки и историю |
| Оператор банка | Обрабатывает исключения |

## 3. Business Requirements

**BR-01.** Система должна автоматически принимать решение по заявке на потребительский кредит на основании данных клиента и результата скоринговой модели.

**BR-02.** Система должна сохранять сведения о заявке и историю изменения её статуса.

**BR-03.** Система должна предоставлять клиенту результат обработки заявки через REST API.

**BR-04.** Система должна обеспечивать трассируемость ключевых действий над заявкой.

## 4. Functional Requirements

- **FR-01** — система должна принимать заявку через REST API.
- **FR-02** — система должна валидировать обязательные поля.
- **FR-03** — система должна проверять формат паспортных данных.
- **FR-04** — система должна присваивать заявке статус `CREATED`.
- **FR-05** — система должна переводить заявку в `VERIFICATION`.
- **FR-06** — система должна передавать заявку в скоринговый сервис.
- **FR-07** — система должна рассчитывать кредитный рейтинг.
- **FR-08** — система должна принимать решение `APPROVED` или `REJECTED`.
- **FR-09** — система должна сохранять историю изменения статуса.
- **FR-10** — система должна возвращать заявку по идентификатору.
- **FR-11** — система должна возвращать историю обработки заявки.
- **FR-12** — одобренная заявка должна иметь возможность перейти в `CONTRACT`.

## 5. Non-Functional Requirements

- **NFR-01 Performance** — целевое время ответа стандартного API-запроса: менее 500 мс.
- **NFR-02 Availability** — целевая доступность production-системы: 99,9%.
- **NFR-03 Auditability** — каждое изменение статуса должно сохраняться в истории.
- **NFR-04 Idempotency** — повторная отправка одного логического POST-запроса не должна создавать дубликат.
- **NFR-05 Security** — персональные данные должны передаваться по защищённому соединению и храниться с применением соответствующих мер защиты.
- **NFR-06 Validation** — некорректные входные данные должны отклоняться.
- **NFR-07 Observability** — API и критические бизнес-операции должны логироваться.
- **NFR-08 Scalability** — scoring service должен иметь возможность быть вынесен в отдельный сервис.

## 6. Бизнес-правила MVP

- Score >= 650 → `APPROVED`.
- Score < 650 → `REJECTED`.
- `APPROVED` → `CONTRACT`.
- Недопустимый переход статуса запрещён.

## 7. Ограничения

1. Реальные KYC/AML-проверки не реализуются.
2. Реальный БКИ заменён mock-логикой.
3. Авторизация API в MVP не реализована.
4. Скоринговая формула является учебной.
5. SQLite используется для локального запуска; PostgreSQL — целевая СУБД.
